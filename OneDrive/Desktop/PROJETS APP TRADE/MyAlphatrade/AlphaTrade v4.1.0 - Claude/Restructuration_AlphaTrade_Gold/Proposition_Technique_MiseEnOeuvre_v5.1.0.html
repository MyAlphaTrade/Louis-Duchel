Corrections intégrées (2 passes)

Passe 1 — Louis, 31/07/2026

KB8 n'était pas « en attente de branchement » — déjà branché et testé en live, puis retiré car il causait des pertes réelles. Traité depuis comme un diagnostic obligatoire, pas une finalisation. Les types d'ordre ne se limitent pas à Buy/Sell Limit — tous les types doivent être possibles, la sélection étant pilotée par strategy_mode.

Passe 2 — Louis, 31/07/2026, relecture de cette proposition

Neuf précisions structurantes, intégrées dans ce document : (1) enveloppe de métadonnées sur chaque compartiment de la Shared Memory (timestamp/source/confidence/version/valid_until) ; (2) contrat unique AgentReport pour tous les rapports d'agent ; (3) le CAIO compare des recommandations complètes, jamais des scores nus ; (4) entry_policy devient une préférence que le CAIO peut outrepasser selon le contexte, pas une contrainte absolue ; (5) diagnostic KB8 structuré autour de 4 questions précises obligatoires ; (6) Mission Manager publie beaucoup plus (objectifs jour/semaine/mois, état psychologique, agressivité, risque, mode) ; (7) notion de priorité (CRITICAL/HIGH/MEDIUM/LOW) sur chaque rapport ; (8) règle d'or explicite sur le chemin unique vers MT5 ; (9) le contrat CAIO est conçu dès 5.1.0 pour accueillir le futur Scenario Generator sans refonte en 5.1.1.

Règle d'or de l'implémentation

Ajoutée par Louis — à respecter dans tout code futur

« Aucun agent n'est autorisé à déclencher directement un ordre MT5. Tous les agents proposent, seul le CAIO décide, et seul l'Execution Manager exécute. »

Un seul chemin de décision vers le marché. Concrètement : aucune fonction agent (risk_manager_report(), structure_analyst_report(), smart_money_analyst_report(), mission_state()...) n'a accès à mt5.order_send. Seule place_order() (appelée uniquement depuis le résultat de caio_decide()) touche MT5.

Contrat unifié — AgentReport

Aujourd'hui chaque rapport (Risk Report, Structure Report, Smart Money Report) aurait sa propre forme ad hoc. Louis a raison : un seul format, plus évolutif, plus simple à arbitrer pour le CAIO.

ChampDescription
agentIdentifiant de l'agent émetteur (ex : "structure_analyst").
statusOK / DEGRADED (données partielles, ex : MT5 brièvement déconnecté) / UNAVAILABLE (aucun rapport ce cycle). Le CAIO traite DEGRADED/UNAVAILABLE avec méfiance quelle que soit la confiance affichée.
confidence0-100, propre à l'agent.
priorityCRITICAL / HIGH / MEDIUM / LOW — un rapport CRITICAL (ex : Risk Manager signalant un dépassement) prime sur tout rapport LOW/MEDIUM favorable, quelle que soit sa confiance.
recommendationObjet structuré, jamais un simple nombre — ex : {action:"BUY_LIMIT", price:2385.40}, {action:"WAIT"}, {action:"RISK_CAP", max_risk_pct:0.6}.
argumentsListe de raisons à l'appui de la recommandation.
risksListe de raisons de s'en méfier.
expirationvalid_until — au-delà, le rapport est considéré périmé et ignoré par le CAIO même s'il est encore présent en mémoire.
metadataChamp libre propre à l'agent (ex : timeframe utilisé, zone source).

Toute fonction d'agent retourne exactement cette forme — risk_manager_report(), structure_analyst_report(), smart_money_analyst_report() notamment. Le CAIO ne reçoit jamais qu'une List[AgentReport], jamais un format spécifique par agent.

Décision d'architecture centrale : où vit cette nouvelle intelligence ?

Deux mécanismes de sélection existent déjà dans le code : active_engine (AlphaTrade AI vs KB1000 Gold AI, ENGINE_REGISTRY) et strategy_mode (scalping_fast/scalping_safe/long_analysis/combined, STRATEGY_PROFILES). Créer un troisième mécanisme pour la nouvelle couche serait redondant. Décision, validée par Louis :

La nouvelle couche (Mission Manager, CAIO v1, Structure/Smart Money Analyst) devient une infrastructure partagée entre les deux moteurs. strategy_mode devient l'endroit où l'on choisit une préférence d'entrée — pas une contrainte absolue (correction de Louis, voir ci-dessous) :

STRATEGY_PROFILES = {
  "scalping_fast": {..., "entry_policy": "immediate"},
  "scalping_safe": {..., "entry_policy": "immediate"},
  "long_analysis": {..., "entry_policy": "pending_limit"},
  "combined":      {..., "entry_policy": "adaptive"},
}

immediate (préférence)

Le CAIO privilégie BUY/SELL MARKET. Modes scalping — rapide, toujours informé par Structure/Smart Money/Risk.

pending_limit (préférence)

Le CAIO privilégie BUY/SELL LIMIT, ancrés sur les zones de Structure/Smart Money. Modes d'analyse plus posée.

adaptive

Aucune préférence fixe — le CAIO choisit librement, y compris Buy/Sell Stop sur cassure confirmée.

Nuance de Louis, intégrée : « le strategy_mode doit exprimer une philosophie, pas imposer totalement le type d'ordre ». Exemple donné : en scalping, préférence Market, mais si le prix est à 30 points d'une zone idéale, le CAIO doit pouvoir dire « finalement, Buy Limit ». Le contexte garde le dernier mot. Concrètement : entry_policy n'est plus un filtre dur consommé par place_order(), c'est un défaut lu par caio_decide(), qui peut s'en écarter — chaque écart est journalisé (caio.entry_override, écrit dans shared_memory["learning_history"] avec la raison) pour rester traçable et mesurable a posteriori.

Bénéfice collatéral inchangé : ça force à corriger le bug de désync de strategy_mode déjà documenté dans l'audit Phase 3 (3 définitions indépendantes : STRATEGY_PROFILES Python, strategyProfiles renderer.js, <option> index.html). STRATEGY_PROFILES devient la source de vérité unique, sélecteur UI généré dynamiquement.

Le CAIO arbitre des rapports, pas des scores

Erreur à éviter, signalée par Louis : réduire le CAIO à un fusionneur de pourcentages (Structure 83% + Smart Money 76% → moyenne). Avec le contrat AgentReport ci-dessus, le CAIO compare de vraies hypothèses :

caio_decide(reports: List[AgentReport], mission_state, entry_policy) — logique d'arbitrage en deux temps : (1) tout rapport CRITICAL est vérifié en premier et peut à lui seul imposer une contrainte dure (ici : aucun trade au-delà de 0.6% de risque, quelle que soit l'opinion de Structure/Smart Money) ; (2) parmi les recommandations restantes compatibles avec la contrainte, le CAIO compare les hypothèses entre elles (pas juste leurs confidences isolées) — un WAIT avec de bons arguments peut l'emporter sur un BUY LIMIT plus confiant, exactement comme documenté dans l'Architecture doc. Retour : {decision: GO|NO_TRADE, order_type?, price?, raison, overrides:[...]}.

KB8 / gestion de position — diagnostic avant tout

Renforcé par Louis : aucune réintégration sans avoir documenté, par écrit, la réponse à ces 4 questions précises. Tant qu'elles ne sont pas répondues, KB8 reste désactivé — pas de zone grise.

1 — Pourquoi a-t-il perdu ?
Cause racine identifiée à partir des logs, pas une hypothèse.
2 — Qu'est-ce qui est faux ?
Le composant précis en cause (stop trop serré ? lot mal calibré ? BE prématuré ?).
3 — Qu'est-ce qu'on corrige ?
Le changement concret proposé, pas une réactivation telle quelle.
4 — Comment prouve-t-on que c'est corrigé ?
Le test/la période démo qui validera la correction avant tout retour en réel.

Méthode pour répondre aux questions 1 et 2, à partir des données déjà existantes (aucun nouveau code nécessaire pour l'investigation) : retrouver la période où KB8 était actif via alphatrade.log et l'historique trades.json/alphatrade.db ; comparer les sorties gérées par manage_position() (KB8) à celles de position_exit_reason() (générique) sur la même période ou en avant/après activation (trade_exits.jsonl/rebond_log.jsonl exploitables directement). Hypothèses prioritaires à vérifier : stop de stop_placement_from_structure() trop serré pour les mèches fréquentes de l'or ; lot de calculate_lot() en double comptage avec real_lot_cap ; Break-Even (break_even_trigger()/break_even_level()) déclenché trop tôt.

Issue : questions répondues + correction validée en démo → réintégration possible, mais en fin de construction 5.1.0 (jamais en tête). Problème de conception plus profond révélé → reporté à une refonte 5.1.1.

Mission Manager — ce qu'il publie

Louis demande d'aller au-delà du simple objectif/perte max. mission_state() publie désormais, dans shared_memory["trading_objectives"] :

ChampDéfinition proposée
daily_target / weekly_target / monthly_targetObjectifs $ par horizon — les deux derniers sont nouveaux (aujourd'hui limités à la session/jour).
psychological_stateHeuristique de trajectoire récente — Neutre / Sous pression (série de pertes ou drawdown qui s'approche des limites) / Confiant (série de gains, objectif en bonne voie). Pas une vraie mesure psychologique, un état dérivé nommé dans le langage du trader professionnel.
aggressiveness_levelScalaire 0-100 dérivé du mode + de l'état psychologique + de la proximité de l'objectif. Module la sélectivité du CAIO (seuil de confiance minimum) et le sizing proposé au Risk Manager.
risk_appetiteBudget de risque au niveau mission (macro, journée/semaine) — distinct du budget du Risk Manager qui reste au niveau trade (micro, ce cycle précis). Le second ne peut jamais dépasser le premier.
modeNormal / Prudent / Défense / Protection (inchangé depuis l'Architecture doc).

Tous les agents en aval (Risk Manager, Scenario/CAIO) lisent cet état enrichi plutôt qu'un simple booléen mode — aggressiveness_level et psychological_state sont les deux champs proposés par cette proposition (pas explicitement nommés par Louis dans le détail de leur calcul) : formule exacte à valider avec lui avant codage, voir Questions ouvertes.

Types d'ordre MT5 — détail technique

Le moteur pose déjà des ordres Market (open_position()/send_deal(), TRADE_ACTION_DEAL). Les 4 types en attente sont nouveaux, tous disponibles quel que soit le mode (la préférence n'est plus une restriction, voir plus haut) :

TypeConstante MT5Point d'attention
Buy Limit / Sell LimitORDER_TYPE_BUY_LIMIT / ORDER_TYPE_SELL_LIMITPrix doit respecter la distance minimale broker (symbol_info().trade_stops_level) — à valider avant envoi, sinon rejet MT5.
Buy Stop / Sell StopORDER_TYPE_BUY_STOP / ORDER_TYPE_SELL_STOPDéclenchés uniquement quand le CAIO dispose d'une confirmation Smart Money Analyst (évite d'entrer sur un faux breakout) — pas réservés à un seul mode puisque entry_policy n'est plus un filtre dur.
Gestion des ordres en attente non déclenchés—Expiration (ORDER_TIME_SPECIFIED) ou annulation si le contexte change avant déclenchement (ex : le rapport Structure qui l'a justifié expire — voir valid_until).

Shared Market Memory — implémentation

Toujours un dict Python en mémoire process (shared_memory.py), pas de nouvelle base de données. Mais chaque compartiment n'est plus une valeur brute — c'est une enveloppe :

shared_memory["structures"] = {
  "created_at": "2026-07-31T14:22:03Z",
  "source": "structure_analyst",
  "confidence": 86,
  "version": 214,
  "valid_until": "2026-07-31T14:27:03Z",
  "payload": { ...AgentReport complet... }
}

Ainsi le CAIO sait immédiatement qui a produit l'information, quand, et si elle est encore valable — une information vieille de 30 minutes n'a pas la même valeur sur M1 que sur H4. version s'incrémente à chaque écriture (aide au débogage, détecte une lecture obsolète). Pour les compartiments qui ne sont pas des recommandations d'agent (open_positions, performance — de l'état factuel, pas une opinion), confidence reste fixée à 100 et payload contient la donnée brute plutôt qu'un AgentReport.

9 compartiments pour 5.1.0 : market_context, structures, smart_money, liquidity, risk, open_positions, trading_objectives, performance, learning_history. Contrat « un agent n'écrit que dans son compartiment » appliqué en code. Snapshot JSON optionnel (data/shared_memory_debug.json) pour le débogage, jamais une source de vérité persistante.

Réservé pour la v5.1.1 — Scenario Generator

Même si le Scenario Generator n'est pas construit en 5.1.0, la signature de caio_decide(reports: List[AgentReport], ...) est conçue pour l'accueillir sans refonte : en 5.1.0, chaque agent produit exactement un AgentReport par cycle, donc le CAIO reçoit une petite liste (Structure, Smart Money, Risk...). En 5.1.1, quand le Scenario Generator existera, il pourra produire plusieurs AgentReport candidats (un par scénario, ex : Scénario A/B/C de l'Architecture doc) à partir des mêmes signaux amont — le CAIO recevra simplement une liste plus longue, sans que sa fonction ni sa logique d'arbitrage priorité→hypothèses ne changent.

Aujourd'hui (5.1.0) :  Structure ─┐
                                   ├─► CAIO
Demain (5.1.1) :       Structure ─┤
                        Scenario Generator (N scénarios) ─┘

Plan de sécurité et de déploiement

  • Chaque élément qui touche l'exécution réelle (stop-loss, types d'ordre, décision CAIO) est d'abord testé en compte démo, comparaison explicite avant/après sur une période équivalente — jamais activé directement en réel.
  • Nouveau paramètre global gold_brain_enabled (défaut False), bascule instantanée vers l'ancien comportement — même philosophie que rebond_enabled/active_engine.
  • Règle d'or (voir section dédiée) appliquée dès le premier commit touchant l'exécution : revue de code systématique pour vérifier qu'aucun agent n'appelle mt5.order_send hors de place_order().
  • Leçon de KB8 appliquée à tout le reste : aucune fonctionnalité de gestion de position (stop, BE, trailing) n'est introduite sans session de tests démo dédiée.

Plan de tests

Suit la convention déjà établie : scripts isolés test_*.py, sans dépendance MT5 quand possible, zéro régression sur les suites existantes (13 Phase 1 + 48 scénarios KB1-KB8 + 5 registre). Nouveaux scripts :

  • test_agent_report_contract.py — tous les wrappers retournent une forme conforme (champs obligatoires, status/priority valides).
  • test_strategy_profiles_registry.py — cohérence du registre unifié, entry_policy par profil.
  • test_shared_memory.py — enveloppe (version incrémentale, valid_until expire bien un rapport périmé), contrat lecture/écriture par compartiment.
  • test_mission_manager.py — graduation des modes, horizons semaine/mois, cohérence aggressiveness_level/psychological_state.
  • test_caio_v1.py — rapport CRITICAL qui prime sur des rapports favorables ; désaccord entre hypothèses ; aucun candidat suffisant → NO_TRADE ; override d'entry_policy correctement journalisé.
