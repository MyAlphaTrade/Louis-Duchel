Résumé

Le verdict en une minute

Le taux de perte n'est pas un problème de "moteurs pas assez intelligents" — c'est un problème de plomberie. Deux bugs structurels précis expliquent l'essentiel du solde négatif, et sont corrigibles cette semaine sans toucher à un seul algorithme.

Le point plus sérieux, celui qui répond directement à ta question « pourquoi les moteurs restent bref » : les 19 moteurs d'analyse ne regardent aucune donnée de marché réelle. Ni bougies, ni indicateurs calculés, ni niveaux de prix — le Market Brain envoie un prompt texte à un LLM et lui demande de jouer le rôle de 19 experts. C'est de la mise en scène convaincante, pas de l'analyse quantitative.

02 · Bilan honnête

Ce qui tient déjà la route

Un audit qui ne liste que des problèmes n'est pas fiable. Voici ce qui est du travail solide et ne doit pas être touché.

  • Le build passe proprement. npm run build compile sans erreur (2945 modules), npm run lint ne remonte que 12 imports inutilisés — du code propre pour un projet de cette taille.
  • Le pont MT5 (alphatg_bridge.py) est du travail sérieux — retry automatique sur les modes de remplissage d'ordre (retcode 10030), décodage des codes d'erreur MT5 en messages exploitables, ajustement automatique SL/TP au minimum du broker, flux SSE temps réel (~200 ms) plutôt qu'un polling lent.
  • Le calcul de lot est correctement basé sur le risque (alphatradeConnector.ts — lot = risque% × capital / distance-SL), pas une taille fixe en dur.
  • L'architecture à 19 domaines est une bonne colonne vertébrale. Séparer Structure de marché / Smart Money / Volume / Liquidité / Risque / Exécution en modules nommés et pondérés est la bonne façon de penser le problème — le défaut n'est pas la structure, c'est ce qui la remplit (section suivante).
  • 10 pages fonctionnelles couvrant tout le cycle (Analysis, StrategyTester, Journal, ValidationCenter, ClientSpace) — le socle produit existe déjà.
03 · Diagnostic

Les causes racines, avec preuves

1 — L'ancien moteur AlphaTrade tue les trades du nouveau

Critique
Impact mesuré : environ 100 $ des 280 $ de perte nette (36 %) proviennent directement de ce bug.

L'ancien moteur (AlphaTrade v4.1.0/5.0.0, magic 20260607) identifie l'origine d'une position par mot-clé dans le commentaire MT5 quand le magic ne correspond pas : sa règle "AlphaTrade AI" matche tout commentaire contenant "alphatrade". Or AlphaTrade Global tague ses propres ordres avec le commentaire "AlphaTrade Global" — qui contient bien sûr le mot "alphatrade".

Résultat : l'ancien moteur adopte les positions d'AlphaTrade Global comme les siennes et leur applique sa propre logique de protection (MAX_FLOATING_LOSS, MAX_POSITION_LOSS, trailing) — avec des seuils qui n'ont rien à voir avec la stratégie d'AlphaTrade Global.

alphatrade_engine.py:67-68 — règle de correspondance : {"name": "AlphaTrade AI", "magic_numbers": [MAGIC], "comment_keywords": ["alphatrade", "alphakaris"]} data/trade_exits.jsonl — 5 positions XAUUSD d'AlphaTrade Global forcées à la fermeture par l'ancien moteur le 27/07 à 23:21-23:24 : ticket 9735532848 → MAX_FLOATING_LOSS → -27,99 $ ticket 9735535459 → MAX_FLOATING_LOSS → -27,36 $ ticket 9735536554 → MAX_FLOATING_LOSS → -26,68 $ ticket 9735592444 → MAX_POSITION_LOSS → -18,05 $ ticket 9735675507 → PROFIT_TRAILING → -0,58 $ (était à +0,16 $ juste avant)

Les deux moteurs tournaient donc en même temps sur le même compte, sans le savoir l'un de l'autre.

2 — Les 19 moteurs n'analysent aucune donnée de marché

Critique
C'est la vraie raison pour laquelle les moteurs restent « bref ».

base44/functions/marketBrain/entry.ts — la fonction buildPrompt() — construit un unique prompt texte envoyé au LLM. Il contient : le nom du symbole, le timeframe, une description générique de chaque moteur ("Focus: EMA, SMA, VWAP, MACD, RSI…"), l'historique d'apprentissage, et l'état du compte. Aucune bougie, aucun prix historique, aucun indicateur calculé n'y figure.

Le LLM reçoit littéralement l'instruction "Analyse XAUUSD sur H1 maintenant" et doit inventer les niveaux de Fibonacci, les Order Blocks, la structure de marché — sans avoir vu un seul prix. Le paramètre add_context_from_internet peut ramener un peu de contexte via une recherche web (et seulement pour le fournisseur Gemini — aiInvoke.ts:44 désactive cette option pour OpenAI/Anthropic), ce qui est beaucoup trop imprécis pour fixer un niveau d'entrée ou un Stop Loss au dollar près.

marketBrain/entry.ts:125-153 function buildPrompt(symbol, timeframe, context) { ... // noms de moteurs + descriptions statiques + contexte compte // → zéro série de prix, zéro OHLC, zéro indicateur calculé }

Concrètement : le score de confiance, le Stop Loss, les Take Profit affichés sont game de rôle bien structuré, pas un calcul. C'est cohérent avec les résultats observés — de bonnes intuitions générales par moments, mais aucune précision fiable sur les niveaux de prix.

3 — Le backtest et les tests de validation sont fabriqués, pas simulés

Majeur
Conséquence : impossible de valider une amélioration de stratégie avec les outils actuels.

strategyTester/entry.ts:84-90 demande au LLM de « simuler les trades qu'aurait pris un trader discipliné » et de « calculer » profit factor, drawdown, gain moyen — le tout sans jeu de données historiques réel en entrée. Le résultat est un JSON plausible, pas un backtest reproductible : deux exécutions du même test sur la même période peuvent donner des chiffres différents, et rien ne garantit que les prix "simulés" aient existé.

Idem pour engineTest/entry.ts (Centre de Validation) : chaque test de moteur est un unique appel LLM avec un prompt spécialisé — utile pour vérifier que le pipeline répond, inutile pour vérifier que l'analyse est juste.

4 — Aucune gestion de position après l'ouverture

Majeur
Explique directement l'asymétrie gain/perte (0,32 profit factor).

Une fois un ordre envoyé (AnalysisSessionStore.jsx:61-90), rien ne surveille plus la position côté AlphaTrade Global : pas de passage à break-even, pas de trailing stop, pas de sortie partielle au premier objectif. La position attend son Stop Loss ou son Take Profit fixe, point final — ce que le registre des moteurs appelle « Position Management » et « Autonomous Trading » n'existe que comme texte descriptif dans le prompt LLM (engineTest/entry.ts:34,41), sans code qui l'exécute réellement sur MT5.

C'est cohérent avec les positions AUDUSD tenues 1 à 2 jours avant un Stop Loss, et avec les micro-gains XAUUSD (0,21-0,38 $) : sans gestion active, un take profit trop proche capture des miettes et un mouvement défavorable prend tout son temps pour toucher le stop.

5 — Le trading « autonome » ne tourne que si un onglet est ouvert

Modéré

La boucle de scan (AnalysisSessionStore.jsx:138-148) est un setInterval React côté navigateur. Fermer l'onglet, mettre l'ordinateur en veille, ou fermer l'app desktop arrête tout — analyse et gestion comprises. Aucune tâche planifiée côté serveur (Base44 cron) ne prend le relais. L'ancien moteur Python, lui, tourne en processus permanent 24/7 — c'est un vrai recul d'architecture sur ce point précis.

6 — Détails de code mineurs

Mineur

12 imports inutilisés (corrigibles avec npm run lint:fix), et un bundle JS de 1,1 Mo non découpé (vite.config.js — manualChunks à configurer). Aucun impact sur le trading, juste de l'hygiène.

05 · En réponse directe

Est-ce déjà meilleur qu'AlphaTrade ?

Non, pas encore — mais pas pour la raison qu'on pourrait croire. Ce n'est pas que les idées (19 domaines d'analyse, entry planner, gestion du risque) soient moins bonnes. C'est que l'ancien moteur, malgré son code plus rigide, calcule réellement ses indicateurs sur des prix réels, alors qu'AlphaTrade Global délègue cette analyse à un LLM qui n'a jamais vu un seul prix. Un système qui calcule juste avec une stratégie simple bat un système qui raisonne bien sur des données inventées.

La bonne nouvelle : la structure d'AlphaTrade Global (les 19 moteurs, l'architecture multi-plateforme, le pont MT5 temps réel, l'UI complète) est un meilleur socle pour construire la vraie intelligence que ne l'était le code monolithique de l'ancien moteur. Il manque une seule chose, mais elle est centrale : brancher des données de marché réelles derrière chaque moteur. Une fois ce fil branché, l'architecture existante est prête à en tirer parti sans tout reconstruire.

Audit basé sur lecture de code (frontend + fonctions Base44 + pont Python), extraction en lecture seule de l'historique MT5 réel, et exécution du build/lint du projet. Aucun ordre n'a été passé ni modifié pendant cet audit.
